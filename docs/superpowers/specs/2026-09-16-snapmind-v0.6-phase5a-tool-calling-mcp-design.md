## Goal

Make the model able to _do_ things, not just write. Main runs `@ai-sdk`'s tool loop, tools come from user-configured MCP servers, each agent declares which tools it may use, and the user approves anything sensitive before it runs.

## Deviation from the roadmap: Phase 5 is split

The roadmap's Phase 5 bundles four subsystems: the tool loop, an MCP host, folder-based skills, and a permission model. That is more than one spec should carry — phases 1–4 each stayed near a single subsystem.

| Sub-phase | Scope                                              | Ships as                            |
| --------- | -------------------------------------------------- | ----------------------------------- |
| **5a**    | Tool loop + MCP client host + allowlist + approval | `0.6.0-beta.6`                      |
| **5b**    | Skills as folder-based bundles                     | `0.6.0-beta.7` or `0.7.0`, per §9.1 |

**Why tools-and-MCP first.** The tool loop is the foundation both tool sources sit on, and MCP delivers value on day one — a large ecosystem of servers already exists, so the feature is useful before anything is authored. Skills raise an unresolved question of their own (is a skill a _tool the model calls_, or _instructions injected into context_? Claude Code is closer to the latter) and bundling that with MCP transport lifecycle is what makes the roadmap's Phase 5 too big.

🔸 **Where GA lands is undecided.** Either 5a ships as `0.6.0` GA and skills become 0.7.0, or betas continue until 5b lands. This spec assumes `0.6.0-beta.6` and leaves GA open.

## What the AI SDK already gives us

Research against the installed `ai@7.0.89` changed the shape of this design substantially. Much of what the roadmap imagined as custom code is SDK-native:

| Need                          | SDK facility                                                        |
| ----------------------------- | ------------------------------------------------------------------- |
| Tool loop (call → run → call) | `streamText({ tools, stopWhen: stepCountIs(n) })`                   |
| Per-agent allowlist           | `activeTools`                                                       |
| User consent                  | `toolApproval` + `tool-approval-request` / `tool-approval-response` |
| Runaway tool protection       | `timeout: { toolMs, stepMs, totalMs }`                              |
| MCP client                    | `@ai-sdk/mcp` `createMCPClient` (stdio + HTTP + SSE)                |
| MCP "rug pull" defense        | `fingerprintTools` + `detectToolDrift`                              |

Consequences: we write **no** tool-loop state machine, **no** consent protocol, and **no** MCP wire client. Phase 5a is mostly configuration storage, lifecycle, IPC, and UI.

Note `needsApproval` on `tool()` is deprecated in v7; approval goes through `toolApproval` on `streamText`.

## Non-goals

- No skills / `SKILL.md` / folder bundles. That is 5b.
- No MCP **resources** or **prompts** — tools only.
- No OAuth for remote MCP servers. Static headers only. (`@ai-sdk/mcp` supports `authProvider`; wiring a browser OAuth dance into Electron is its own project.)
- No tool-drift baseline storage. `fingerprintTools` exists; adopting it is a follow-up. Called out in Risks.
- No sandboxing of MCP subprocesses. They run with the app's privileges. See Risks — this is the sharpest edge in 5a.
- No marketplace, no server discovery/registry. Users paste a command or URL.
- No auto-selection of agents by the model. Hotkeys still choose the agent.
- No change to provider / model / hotkey schema.

## Success criteria

1. A user can add an MCP server in Settings > Tools, see its tools discovered, and enable them for an agent.
2. With that agent, a chat turn that needs a tool calls it, shows the call and its result in the transcript, and the model's follow-up answer uses the result.
3. A tool marked as needing approval pauses the run, shows an approve/deny prompt, and resumes correctly on either choice.
4. An agent's allowlist is enforced in main — a tool not on the list is never offered to the model.
5. Only models whose `capabilities` include `tools` get a `tools` payload. Others behave exactly as beta.5.
6. A broken MCP server (bad command, crash, timeout) degrades gracefully: the run proceeds with remaining tools and the failure is visible in Settings, not as a dead chat.
7. Secrets in MCP config (env vars, headers) are encrypted at rest via `SafeStorageService` and never logged.
8. Abort cancels mid-tool-loop, including while awaiting approval.
9. Vitest, lint, `tsc` ×3, and `build` pass.

## §1. Architecture

```
Renderer (useChatStore)                    Main
  ai:send { agentId, messages } ─────────▶ AIService.send
                                             1. resolve agent/provider/model   (as beta.5)
                                             2. model has 'tools' capability?
                                             3. McpHostService.toolsFor(agent) ──▶ MCP servers
                                             4. streamText({ tools, activeTools,
                                                  toolApproval, stopWhen, timeout })
  ◀──── ai:token | ai:reasoning | ai:source ──┤  (unchanged from beta.5)
  ◀──── ai:tool-call    { toolCallId, name, input }
  ◀──── ai:tool-result  { toolCallId, output | error }
  ◀──── ai:tool-approval-request { toolCallId, name, input, reason }
  ai:approve { streamId, toolCallId, approved } ─▶ resume the run
  ◀──── ai:done { reason, modelMessages }
```

**The renderer stays a view.** It renders tool activity and collects the approve/deny click. It never sees an MCP config, a command line, or a header value, and it does not drive the loop.

### §1.1 Run state — the one real change to `AIService`

Beta.5's `AIService.send` is stateless: the renderer owns history, main borrows it for one `streamText` call. **Approval breaks that.** Per the SDK, manual approval takes _two_ model calls — the first returns `tool-approval-request` parts, then the app appends a `tool-approval-response` to the message array and calls again.

So main must hold the in-flight message array across the pause. `InFlight` grows from `{ streamId, controller }` to a `Run`:

```ts
type Run = {
  streamId: string;
  controller: AbortController;
  agentId: number;
  model: LanguageModel;
  tools: ToolSet;
  activeTools: string[];
  params: MappedStreamParams;
  messages: ModelMessage[]; // grows as the loop proceeds
  pending: Map<string, PendingApproval>;
};
```

The run is dropped on `ai:done` / `ai:error` / abort. Still **one run at a time** — a new `send` aborts the previous, exactly as beta.5.

🔸 **Carrying tool context into the next turn.** If turn 1 calls a tool, turn 2's history (sent by the renderer) must still contain the tool call and its result, or the model loses the thread. Proposal: `ai:done` carries the run's canonical `modelMessages`, and the renderer stores them opaquely on the assistant `Message`; `mapMessages` splices them back in on the next send instead of the plain assistant string. The renderer never interprets them.

The alternative — main owning the whole conversation — is a larger change to the chat model and is not proposed here.

### §1.2 Approval pause and resume

1. `streamText` finishes a step with `tool-approval-request` parts.
2. `AIService` records each in `run.pending`, emits `ai:tool-approval-request`, and **stops** — the run stays alive, no timer.
3. Renderer shows the prompt. The user approves or denies.
4. `ai:approve` appends a `tool-approval-response` to `run.messages` and calls `streamText` again with the same `streamId`.
5. Approved → the tool runs and the loop continues. Denied → the model is told and responds accordingly.

Abort during the pause discards the run and emits `ai:done { reason: 'aborted' }`. Closing/hiding the window does **not** cancel — consistent with beta.5's "hide keeps the stream."

🔸 A run awaiting approval holds a subprocess and memory indefinitely. Proposal: no timeout, on the grounds that the popup is user-driven and an arbitrary 60s denial is worse than waiting. Easy to add later.

## §2. MCP host

### §2.1 Components

- `electron/mcp/McpHostService.ts` — class. Owns client lifecycle: connect, discover tools, cache, close. Keyed by server id.
- `electron/mcp/buildTransport.ts` — config row → `@ai-sdk/mcp` transport (stdio via `StdioClientTransport`, or `{ type: 'http', url, headers }`).
- `electron/mcp/namespaceTools.ts` — prefix tool names per server, resolve collisions.
- `electron/services/McpServersService.ts` — CRUD over the new tables, mirroring `ProvidersService` (including the `SafeStorageService` encrypt/decrypt pattern).

### §2.2 Lifecycle

🔸 **Connect lazily, cache, and keep alive.** A server is spawned the first time a run needs one of its tools, then held open for the app's lifetime (or until the user edits/disables it). Rejected alternatives: connect-all-at-startup (slow launch, spawns processes the user may never use) and connect-per-run (a stdio server can take seconds to boot, paid on every hotkey press).

Tool discovery is cached per connection. Settings gets an explicit **Reconnect** action; editing a server closes and forgets its client.

### §2.3 Name collisions

`ToolSet` is a flat record, so two servers exposing `search` would collide. Tools are namespaced `<serverSlug>__<toolName>` — the slug derives from the server name, lowercased, non-`[a-z0-9_-]` stripped. The combined name is truncated to 64 chars to satisfy provider tool-name limits. The model sees the namespaced name; the UI shows the bare name with the server as a subtitle.

### §2.4 Failure handling

A server that fails to start, times out, or crashes mid-run is **not** fatal to the chat. Its tools drop out of the set, the failure is logged and recorded on the server row (`lastError`, `lastConnectedAt`), and Settings shows it. If the failure removes a tool the model already called, the SDK's tool-error path surfaces it as a tool result the model can react to.

If _every_ tool for a run is unavailable, the run proceeds with no tools rather than failing — the model answers from context.

## §3. Data model

Two new tables, following the existing Drizzle + migration framework from Phase 2.

```ts
export const mcpServers = sqliteTable('mcp_servers', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  name: text('name').notNull(),
  transport: text('transport').notNull(), // 'stdio' | 'http'
  command: text('command'), // stdio
  argsJson: text('args_json'), // stdio
  envJson: text('env_json'), // stdio, ENCRYPTED
  cwd: text('cwd'), // stdio
  url: text('url'), // http
  headersJson: text('headers_json'), // http, ENCRYPTED
  enabled: integer('enabled').notNull().default(1),
  lastError: text('last_error'),
  lastConnectedAt: integer('last_connected_at'),
  sortOrder: integer('sort_order').notNull(),
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
});

export const agentTools = sqliteTable('agent_tools', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  agentId: integer('agent_id')
    .notNull()
    .references(() => agents.id, { onDelete: 'cascade' }),
  serverId: integer('server_id')
    .notNull()
    .references(() => mcpServers.id, { onDelete: 'cascade' }),
  toolName: text('tool_name'), // NULL = every tool from this server
  approval: text('approval').notNull().default('ask'), // 'ask' | 'auto'
  createdAt: integer('created_at').notNull(),
});
```

🔸 **A join table, not `agents.configJson`.** The allowlist is queried per run and edited per agent; a table keeps cascade deletes honest when a server is removed. `toolName IS NULL` expresses "trust this whole server," which is the common case and avoids rewriting rows when a server adds a tool.

🔸 **Approval granularity is per allowlist entry**, defaulting to `ask`. Coarser (per-server only) is simpler but cannot say "reading is fine, writing needs a prompt." Finer (per-invocation policy expressions) is over-engineering.

The two stored values map onto the SDK's `toolApproval` per-tool statuses: `ask` → `'user-approval'`, `auto` → `'not-applicable'`. `AIService` builds that map from the agent's allowlist rows; a tool absent from the allowlist never reaches the map because `activeTools` already excluded it.

**Encryption.** `envJson` and `headersJson` hold tokens in practice. They go through `SafeStorageService` exactly as `providers.api_key` does, and `McpServersService` gains the `processApiKeys` equivalent. `redactValue` gets `env`, `headers`, and `token` added to its key pattern.

🔸 **Max steps** (`stopWhen: stepCountIs(n)`) lives on `agents.configJson` as `maxSteps`, default **8**, no schema change. A dedicated column is not worth a migration for one integer.

## §4. IPC contract

New channels; existing ones unchanged.

| Channel                                        | Direction  | Payload                                                          |
| ---------------------------------------------- | ---------- | ---------------------------------------------------------------- |
| `ai:tool-call`                                 | → renderer | `{ streamId, toolCallId, toolName, serverName, input }`          |
| `ai:tool-result`                               | → renderer | `{ streamId, toolCallId, output?, error? }`                      |
| `ai:tool-approval-request`                     | → renderer | `{ streamId, toolCallId, toolName, serverName, input, reason? }` |
| `ai:approve`                                   | invoke     | `{ streamId, toolCallId, approved: boolean }` → `{ ok }`         |
| `mcp:list` / `upsert` / `delete` / `reconnect` | invoke     | mirrors `providers:*`                                            |
| `mcp:tools`                                    | invoke     | `{ serverId }` → discovered tool descriptors                     |
| `agentTools:list` / `set`                      | invoke     | per-agent allowlist CRUD                                         |

`preload.ts` and `src/types/index.d.ts` both change, per the standing contract rule. Renderer payload types live in `src/types/ai-ipc.ts`; the renderer does not import from `electron/`.

`ai:done` gains `modelMessages` (see §1.1).

## §5. Renderer

- **`useChatStore`** — new `toolCalls: Map<toolCallId, ToolCallState>` and `pendingApprovals`. Tool events attach to the current assistant message. Approval resolves through `electronAPI.aiApprove`.
- **`ToolCallCard.tsx`** — collapsed one-liner ("Called `read_file` — _filesystem_") expanding to input/output JSON. Errors render in the existing error style.
- **`ToolApprovalPrompt.tsx`** — inline in the transcript, not a modal: shows server, tool, arguments, and Approve / Deny. A modal would fight the popup's dismiss-on-blur behavior.
- **Settings > Tools** — new page: MCP server list, add/edit form (stdio command+args+env, or HTTP url+headers), connection status, discovered tools, Reconnect.
- **Agent editor** — a Tools section listing servers and their tools with allow + `ask`/`auto` toggles. This reopens the agent editor, which Phase 4 deliberately froze; 5a is where that is allowed.
- Icons go through `src/components/Icon.tsx`, per the standing rule.

## §6. Error handling

| Failure                            | Behavior                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Server won't spawn / connect       | Tools dropped, `lastError` recorded, run continues, Settings shows red                                    |
| Server dies mid-run                | In-flight tool call returns a tool error; model sees it and can recover                                   |
| Tool throws / times out            | SDK tool-error part → `ai:tool-result { error }` → rendered in transcript                                 |
| Model calls a non-allowlisted tool | Impossible — `activeTools` is the filter; a stray call yields `NoSuchToolError`, surfaced as a tool error |
| `stopWhen` limit hit               | Loop stops, `ai:done { reason: 'stop' }`; transcript shows the truncation                                 |
| Model lacks `tools` capability     | No `tools` passed; identical to beta.5 behavior                                                           |
| Abort during tool execution        | `abortSignal` propagates; run discarded; `ai:done { reason: 'aborted' }`                                  |

## §7. Security and risk

**This is the riskiest phase in v0.6.** A stdio MCP server is an arbitrary local process spawned with the app's privileges — and on Windows, SnapMind asks to run **as Administrator** for global hotkeys. An MCP server spawned there inherits that. Mitigations in 5a:

1. Approval defaults to `ask` for every new allowlist entry; `auto` is an explicit user action.
2. The add-server form states plainly that the command runs with the user's privileges.
3. `fix-path` (already a dependency) resolves PATH for spawned servers so commands behave as they do in a terminal.
4. Env and header values are encrypted at rest and redacted from logs.

Accepted, documented, and **not** solved in 5a: process sandboxing, tool-definition drift (`fingerprintTools` exists but is unused), and prompt injection reaching a tool through selected text — the last is inherent to the product's premise and the approval prompt is the only control.

🔸 An option worth a decision: **refuse to host stdio servers when running elevated on Windows**, allowing HTTP transports only. Safer, and unavailable to some users.

## §8. Testing

Following the established pattern — pure functions unit-tested, services tested with injected fakes, no network and no real subprocesses.

- `namespaceTools` — collisions, slugging, 64-char truncation.
- `buildTransport` — stdio vs http config → transport args; secrets decrypted.
- `McpHostService` — fake client factory: lazy connect, cache reuse, failure isolation, close on edit.
- `AIService` — fake `streamText` emitting tool parts: happy-path tool call; allowlist filtering; approval pause → resume approved; resume denied; abort while pending; `stopWhen` limit; model without `tools` capability gets no tools.
- `McpServersService` — CRUD + encryption round-trip against `makeTestDb`.
- `useChatStore` — tool events attach to the right message; approval round-trip.
- Renderer components — `ToolCallCard`, `ToolApprovalPrompt`.
