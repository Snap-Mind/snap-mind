# SnapMind v0.6 Phase 3 — Agent domain model, agents + hotkeys in SQLite

Status: design approved, ready for planning
Owner: Louis Liu
Last updated: 2026-08-20
Parent: [`2026-08-11-snapmind-v0.6-roadmap.md`](./2026-08-11-snapmind-v0.6-roadmap.md)

## Goal

Introduce the agent as the app's unit of AI behavior. An agent owns its instructions, its provider and model binding, and its generation parameters. Hotkeys stop carrying a prompt string and instead reference an agent. Both `agents` and `hotkeys` live in SQLite, so `hotkeys.json` is retired. Settings > Chat is deleted, because every request now resolves its configuration from an agent.

## Deviation from the roadmap

The roadmap's Phase 3 row says `hotkeys.json` gains an `agentId` field and stays a file. This spec moves hotkeys into SQLite instead. The reason is referential integrity: with `hotkeys.agent_id` as a real foreign key, `ON DELETE SET NULL` handles agent deletion, and a dangling reference becomes impossible rather than merely handled. It also deletes code — the hotkey half of `SettingsService`, the file-rewrite step in the importer, and the file mutation that agent deletion would otherwise need. §8 records the roadmap edit.

## Non-goals

- No tool calling, no MCP, no skills, and no `allowedTools` column. Phase 5. `agents.config_json` is the column those will extend.
- No `@ai-sdk` rewrite and no move of `AIService` into main. Phase 4. `AIService` stays in the renderer and keeps its current provider adapters.
- No agent picker in the chat UI. Agents are reached through hotkeys only.
- No change to the number of hotkeys. There are still four rows, and Phase 3 adds no create or delete for them.
- No removal of the providers' non-streaming code path. The user-facing toggle goes away, but `openaiResponseParser` and its siblings keep both branches until Phase 4 replaces them.
- No agent import, export, or sharing.

## Success criteria

1. On fresh install, the DB holds one agent (`Default`, `is_builtin = 1`, unbound) and four hotkey rows. Hotkey 1 is `mode = 'chat'` bound to `Default`; hotkeys 2 through 4 are `mode = 'selection'` with `agent_id IS NULL` and `enabled = 0`.
2. On upgrade from `0.6.0-beta.2`, every hotkey that carried a `prompt` becomes an agent named `Agent 1` … `Agent N` with that prompt as its instructions, and the matching hotkey row references it. The user's `settings.chat` generation parameters land in the `Default` agent's `config_json`. `hotkeys.json.pre-agents.bak` is left on disk and `hotkeys.json` is gone.
3. Pressing `CommandOrControl+\`` opens the window for manual typing on the `Default` agent. It captures no selection and sends nothing.
4. Pressing an assigned selection hotkey captures the selection, seeds the agent's instructions as the system message, and streams a reply using the agent's bound model and parameters.
5. An agent with no binding, a deleted provider, or a deleted model produces an actionable error in the chat naming the agent, not a silent fallback and not a crash.
6. Deleting a provider unbinds its agents. Deleting an agent unassigns its hotkeys. Deleting the `Default` agent is refused.
7. Settings > Chat is gone from the tree, along with its route, category entry, and i18n keys. `settings.json` holds only `general`, `appearance`, and `builtinsSeeded`.
8. The chat input has no model picker. It shows a read-only `agent · model` badge that opens that agent's editor.
9. Existing Vitest suites pass. New suites cover the schema and seed, `AgentsService`, `HotkeysService`, the one-shot import, `useAgentsStore`, and `useHotkeysStore`.

## §1. Storage layer

### 1.1 Schema — `electron/db/schema.ts` additions

```ts
export const agents = sqliteTable('agents', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  name: text('name').notNull(),
  description: text('description'),
  instructions: text('instructions').notNull().default(''),
  providerId: integer('provider_id').references(() => providers.id, { onDelete: 'set null' }),
  modelId: integer('model_id').references(() => providerModels.id, { onDelete: 'set null' }),
  configJson: text('config_json'),
  isBuiltin: integer('is_builtin').notNull().default(0),
  sortOrder: integer('sort_order').notNull(),
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
});

export const hotkeys = sqliteTable('hotkeys', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  accelerator: text('accelerator').notNull(),
  mode: text('mode').notNull().default('selection'),
  agentId: integer('agent_id').references(() => agents.id, { onDelete: 'set null' }),
  enabled: integer('enabled').notNull().default(1),
  sortOrder: integer('sort_order').notNull(),
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
});

export type AgentRow = typeof agents.$inferSelect;
export type HotkeyRow = typeof hotkeys.$inferSelect;
export type HotkeyMode = 'chat' | 'selection';
```

Three schema decisions worth stating:

- **`provider_id` and `model_id` are nullable, but the UI treats them as required.** The agent editor refuses to save without both. Nullability exists because a fresh install has no models at all — `provider_models` starts empty and `resolveDefault` returns `null` — so a `NOT NULL` binding could not be satisfied at seed time.
- **`model_id` needs its own `SET NULL`.** `provider_models` cascades from `providers`, so a provider deletion silently destroys model rows. Without the second `SET NULL`, an agent would keep a `model_id` pointing at a deleted row.
- **`config_json` instead of columns.** It holds `{ temperature, maxTokens, topP, reasoning, webSearch }`, matching how `providers.config_json` holds `apiVersion` / `projectName` / `entraScope`. Absent keys fall back to the constants already in `AIService` (`0.7`, `2048`, `0.95`). Phase 5 extends the same column rather than running another `ALTER`.

`accelerator` replaces today's `key`, matching Electron's own term and avoiding an ambiguous column name.

### 1.2 Migration `0001` and seed

One migration file creates `agents` first, then `hotkeys`, so the foreign key resolves. Seed rows follow the `0000` convention of `created_at = 0`, `updated_at = 0`:

```sql
INSERT INTO agents (name, description, instructions, provider_id, model_id, config_json, is_builtin, sort_order, created_at, updated_at)
VALUES ('Default', 'Used for manual chat', '', NULL, NULL, NULL, 1, 10, 0, 0);

INSERT INTO hotkeys (accelerator, mode, agent_id, enabled, sort_order, created_at, updated_at) VALUES
('CommandOrControl+`',        'chat',      (SELECT id FROM agents WHERE is_builtin = 1), 1, 10, 0, 0),
('CommandOrControl+Shift+T',  'selection', NULL, 0, 20, 0, 0),
('CommandOrControl+Shift+E',  'selection', NULL, 0, 30, 0, 0),
('CommandOrControl+Shift+S',  'selection', NULL, 0, 40, 0, 0);
```

The three selection hotkeys seed **disabled**. A selection hotkey with no agent can only produce the error from §6, so shipping it enabled would be a trap. The Hotkeys page keeps the enable switch disabled until an agent is assigned, with an inline hint saying so.

Hotkey rows are fixed. Phase 3 adds no way to create or delete them, matching today's fixed set of one default plus three custom.

## §2. Service layer

### 2.1 `electron/AgentsService.ts` (new)

Mirrors `ProvidersService` in shape: constructor takes the Drizzle instance, methods return DTOs with `config_json` unpacked. No `SafeStorageService` involvement, because agents hold no secrets.

```ts
export interface AgentDTO {
  id: number;
  name: string;
  description: string | null;
  instructions: string;
  providerId: number | null;
  modelId: number | null;
  temperature?: number;
  maxTokens?: number;
  topP?: number;
  reasoning?: boolean;
  webSearch?: boolean;
  isBuiltin: boolean;
}
```

- `list()` — ordered by `sort_order`, then `id`.
- `create(input)` — appends at `MAX(sort_order) + 10`, as `ProvidersService.create` does.
- `update(id, patch)` — merges `config_json` the way `ProvidersService.mergedConfigJson` does. Rejects a `name` change on a built-in.
- `delete(id)` — throws when `is_builtin = 1`. Hotkey unassignment happens in SQLite through `ON DELETE SET NULL`, so there is nothing else to clean up.

### 2.2 `electron/HotkeysService.ts` (new)

- `list()` — ordered by `sort_order`.
- `update(id, patch)` — accepts `accelerator`, `agentId`, and `enabled` only. `mode` is seeded and never user-editable.

`main.ts:registerHotkeys` reads from this service instead of `settingsService.getHotkeys()`. `better-sqlite3` is synchronous, so the call behaves like today's file read. The one ordering requirement is that migrations run before `registerHotkeys`, which the existing app-ready sequence already satisfies for providers.

### 2.3 `SettingsService` — what changes

- Remove `getHotkeys`, `updateHotkeys`, `hotkeysPath`, and the `hotkeys.default.json` copy step.
- Remove `resolveAndPersistDefaults`. It existed to resolve `settings.chat.defaultProviderId` / `defaultModelId`, and both fields are gone.
- `settings.default.json` loses its whole `chat` section.

### 2.4 IPC contract — `preload.ts`

Replace the three hotkey channels with a pair that mirrors `providers:*`:

| Removed               | Replaced by                                                       |
| --------------------- | ----------------------------------------------------------------- |
| `hotkeys:get`         | `hotkeys:list` — returns `HotkeyDTO[]`                             |
| `hotkeys:update`      | `hotkeys:update` — new signature `(id, patch)`, no longer whole-array |
| `hotkeys:update-path` | nothing; path-based mutation is gone with the JSON file            |

New agent channels: `agents:list`, `agents:create`, `agents:update`, `agents:delete`. Mutations broadcast `agents:changed` and `hotkeys:changed` with the fresh list, following the existing `providers:changed` pattern, so the chat badge and the Hotkeys page stay current. `hotkeys:update` also re-runs `registerHotkeys`, as the current handler does.

## §3. One-shot import — `electron/db/importAgents.ts`

Follows `runImportIfNeeded` from Phase 2. The trigger is the **presence of `hotkeys.json`** in userData, which is simpler than Phase 2's key-presence check, because the file itself disappears after a successful run.

```ts
export async function runAgentImportIfNeeded(opts: {
  hotkeysPath: string;
  settingsPath: string;
  db: AppDb;
}): Promise<'seeded' | 'imported' | 'skipped'>;
```

On trigger, in one transaction:

1. Copy `hotkeys.json` to `hotkeys.json.pre-agents.bak`.
2. Read `settings.json`. Move `chat.temperature`, `chat.max_tokens`, `chat.top_p`, `chat.reasoningEnabled`, and `chat.webSearchEnabled` into the `Default` agent's `config_json`, so tuned values survive. Bind the `Default` agent to `chat.defaultProviderId` / `chat.defaultModelId` when both still resolve to live rows.
3. For each hotkey carrying a non-empty `prompt`, in file order, insert an agent named `Agent 1` … `Agent N` with that prompt as `instructions`, `is_builtin = 0`, and the same resolved binding as `Default`.
4. Delete the four seeded hotkey rows and insert one row per file entry, in file order, so the file is authoritative even if it holds more or fewer than four entries. `accelerator` comes from `key`, `enabled` from `enabled`, and `agent_id` from the agent created in step 3. `mode` is `chat` for the **first** entry with no `prompt` and `selection` for every other entry; a second prompt-less entry becomes `selection` with `agent_id` null and `enabled = 0`, matching the fresh-install treatment of an unassigned hotkey.
5. Delete `hotkeys.json`.
6. Rewrite `settings.json` without its `chat` section, through the same temp-file-and-rename dance `rewriteSettingsAfterImport` uses.

Imported agents inherit the resolved default binding rather than starting unbound, so an upgrading user's hotkeys keep working without a Settings trip. Naming is positional and generic; the Agents page is where they get renamed.

`chat.streamingEnabled` is dropped, not migrated. Requests always stream from here on.

## §4. Main process — hotkey trigger

`triggerHotkey` keys off `mode` instead of `hotkey.prompt`:

- `mode = 'chat'` — abort any in-flight request, navigate to `/chat`, send `{ agentId }` with no text, show and focus the window. No helper spawn.
- `mode = 'selection'` — as today, but the payload is `{ text, agentId }` and the helper no longer receives a prompt string. `runSelectionHelper` loses its `prompt` parameter and returns `{ text }`.

Agent resolution stays in the renderer, which already has agents and providers hydrated. Main reads no agent rows on the hot path, which also keeps the code close to where Phase 4 needs it.

## §5. Renderer

### 5.1 New stores

`src/stores/useAgentsStore.ts` and `src/stores/useHotkeysStore.ts`, both mirroring `useProvidersStore`: hydrate on mount, CRUD through `window.electronAPI`, refresh from the `*:changed` broadcast. `useSettingsStore` drops its `hotkeys` slice and its `updateHotkey` action.

### 5.2 `useChatStore`

- `currentProviderId` and `currentModelId` are replaced by a single `activeAgentId`.
- `setModel` is deleted along with the picker.
- `resetWithSeed({ text, agentId })` sets `activeAgentId`, then resolves the agent. With text, it seeds `{ role: 'system', content: instructions }` plus the user text and streams. Without text — the `chat` mode hotkey — it clears the session and waits for typing.
- `send()` resolves the active agent the same way, so manual and hotkey sessions share one path.
- `setReasoning` and `setWebSearch` write to the active agent's `config_json` through `useAgentsStore.update`, replacing today's writes to `settings.chat`.
- Resolution failure sets an error message instead of throwing. See §6.

### 5.3 `AIService`

The constructor stops reading `settings.chat` and stops resolving a default provider. It takes the already-resolved agent context:

```ts
new AIService({ provider, model, params });
```

The `DEFAULT_TEMPERATURE`, `DEFAULT_MAX_TOKENS`, and `DEFAULT_TOP_P` constants stay as the fallback for unset `config_json` keys. `DEFAULT_STREAMING_ENABLED` and the `streamingEnabled` field are removed; `stream: true` is passed unconditionally. The `throw` for an unresolvable provider moves up into the store, so the failure renders as a chat message rather than an exception.

### 5.4 Chat UI

Remove the model picker from the chat input. Add a read-only badge showing `{agent.name} · {model.name}` that navigates to `/settings/agents/:id`. When the agent is unbound the badge reads `{agent.name} · not configured` and still links there.

## §6. Error handling

One resolution helper serves the store and the badge, returning either a resolved context or a typed failure:

| Case                                    | Message                                                                             |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| Hotkey has no agent                     | This shortcut has no agent. Assign one in Settings > Hotkeys.                        |
| Agent has no provider or model          | Agent "{name}" has no model. Choose one in Settings > Agents.                        |
| Bound provider or model no longer exists | Agent "{name}" points at a model that no longer exists. Choose a new one.            |
| Provider has no API key                 | Agent "{name}" uses {provider}, which has no API key. Add one in Settings > Models.  |

All four render as the existing `role: 'error'` message, so no new message type is needed, and each names the agent and the page that fixes it. Nothing falls back to another model silently.

The API key check applies only to providers that need one. `ollama` is exempt, since it runs locally against `http://localhost:11434` with no credential. The exemption is by `provider.kind`, which is the same discriminator `ProviderFactory.adapterMap` already uses.

## §7. Settings UI

### 7.1 New page — `src/pages/Settings/Agents/`

Master-detail on the `SettingsModels` pattern: a `Listbox` of agents on the left with add and delete, an editor on the right under nested routes at `/settings/agents/:id`. Editor fields: name, description, instructions textarea, provider select, model select filtered to the chosen provider, the three parameter sliders, and the reasoning and web-search toggles. Save is blocked until a provider and model are chosen — this is where required binding is enforced. For the built-in `Default`, the name field is read-only and delete is hidden.

The category list in `Settings.tsx` gains `agents` between `models` and `hotkeys`.

### 7.2 `SettingsHotkeys`

The prompt textarea becomes an agent `Select` populated from `useAgentsStore`. The enable switch is disabled while `agentId` is null, with an inline hint to assign an agent. The `chat` mode row keeps its descriptive card and shows its agent as a select too, so the manual-chat agent is changeable. Reads come from `useHotkeysStore`; `hotkey.key` becomes `hotkey.accelerator`.

### 7.3 Deletions

`SettingsChat.tsx`, its route, its category entry, and the `settings.chat.*` i18n keys in all three locales. New i18n keys for the Agents page and the §6 errors.

## §8. Known trade-off

Nothing auto-binds the `Default` agent. A fresh install that adds a provider and fetches models still errors on the first chat until the user opens Settings > Agents and picks a model. The §6 error links straight to that editor, so it is one click, but it is an extra step that an automatic backfill would have removed. This was chosen deliberately: an automatic backfill picks a model on the user's behalf, which is the same silent-inference behavior that required binding exists to prevent.

A second, smaller cost: changing models is now a Settings trip rather than a click in the chat input. The clickable badge keeps it to two clicks.

## §11. Manual smoke test

1. Fresh install: DB has one agent and four hotkeys, three of them disabled. `Cmd+\`` opens an empty chat. Chat errors with the unbound-agent message until a model is bound.
2. Bind `Default`, then chat manually. Streaming works and the badge shows the model.
3. Create an agent with instructions and a bound model. Assign it to hotkey 2, enable it, select text in another app, press the hotkey. The reply reflects the instructions.
4. Toggle web search in the chat, reopen Settings > Agents, and confirm the agent's toggle persisted.
5. Delete that agent. Hotkey 2 shows unassigned and its switch is disabled again.
6. Delete the provider it used. Remaining agents show `not configured` and chat gives the missing-model error.
7. Attempt to delete `Default`. It is refused.
8. Upgrade path: install `0.6.0-beta.2`, edit a hotkey prompt and a temperature, upgrade, then confirm the agent carries the edited prompt, `Default` carries the temperature, `hotkeys.json.pre-agents.bak` exists, and `hotkeys.json` is gone.
