# SnapMind v0.6 Phase 1 — Single-window UI + Zustand

Status: design approved, ready for planning
Owner: Louis Liu
Last updated: 2026-08-11
Parent: [`2026-08-11-snapmind-v0.6-roadmap.md`](./2026-08-11-snapmind-v0.6-roadmap.md)

## Goal

Collapse SnapMind's two-window UI (`Settings` + `ChatPopup`) into a single long-lived window rendering both surfaces via routes, and replace the `ServiceProvider` + `SettingsManager` state layer with two Zustand stores. This phase is UI + state only — storage, providers, agents, and the AI runtime stay exactly as they are today.

## Non-goals

- No storage change (JSON files under `userData/` continue to load and save as today).
- No provider or `AIService` change; AI still runs in the renderer.
- No agent domain model, no MCP, no tool calling, no `@ai-sdk`.
- No chat history / tabs / multi-session support.
- No new user-facing settings pages.
- No lint enforcement of the store-boundary convention (§4). Convention only.

## Success criteria

1. On upgrade from v0.5.x, existing users' `settings.json` and `hotkeys.json` load without modification and every setting/hotkey works as before.
2. The Settings window and the ChatPopup window no longer exist as separate `BrowserWindow` instances. `BrowserWindow.getAllWindows().length === 1` at steady state (excluding devtools).
3. Global hotkeys work whether the main window is visible or hidden. A hotkey bound to a prompt (`id !== 0`) while a stream is in flight cancels it, resets the conversation, seeds it with `{selectedText, prompt}`, and shows + focuses the window. The `id === 0` hotkey shows + focuses + resets to an empty conversation (no seeding).
4. Closing the window hides it; the app stays in the tray; `Cmd+Q` or tray > Quit truly quits.
5. `ServiceProvider`, `SettingsManager`, `useSettings` hook, and the two-window IPC channels (`chat-popup:*`) are removed from the tree.
6. Existing Vitest suites pass; new tests cover the two stores and the hotkey-reset flow.

## §1. Window & app lifecycle

### 1.1 Window creation

`main.ts` exposes exactly one factory: `createMainWindow`. It creates a `BrowserWindow` at app-ready time and loads `/#/chat` (dev: `http://localhost:5173/#/chat`, prod: `dist/index.html#/chat`). Dimensions default to 500 × 700 (the current `chatPopupWindow` size); `minWidth`/`minHeight` are lowered enough that a settings screen at 600 × 450 fits when the user resizes up. `frame: true`, `resizable: true`, `alwaysOnTop: false`.

`createSettingsWindow`, `createChatPopupWindow`, `showChatPopup`, `showSettingsWindow` are deleted. `focusOrShowMainWindow` becomes `showMainWindow`.

### 1.2 Hide vs. quit

The window's `close` event is intercepted: `event.preventDefault(); window.hide();`. This applies on all platforms. The only real quit paths are:

- macOS: `Cmd+Q` (Electron's default `before-quit`), tray > Quit, or the existing `app:quit` IPC (`electronAPI.quitApp`, preserved from today's preload).
- Windows/Linux: tray > Quit, or the existing `app:quit` IPC.

A flag `app.isQuitting` (set by any Quit path via `app.on('before-quit')`) short-circuits the close-intercept so the real quit proceeds. The existing `app:quit` IPC handler flips this flag before calling `app.quit()`.

### 1.3 macOS activation policy

`app.setActivationPolicy` toggles between `'regular'` (dock icon visible) when the window is visible and `'accessory'` (tray-only) when it's hidden. This preserves today's dock-visibility behaviour without introducing a new mode. `app.on('activate')` (dock-click) calls `showMainWindow`.

### 1.4 Global hotkey flow

Unchanged in shape, condensed in code:

1. `globalShortcut.register(key, ...)` fires the handler in main.
2. Handler spawns `helper/selectedtext` (macOS) or `SelectedTextWin.exe` (Windows), parses JSON stdout.
3. Handler cancels any in-flight AI request. In Phase 1 that means sending the renderer a `chat:abort` IPC before the reset — the renderer's `useChatStore.abort()` calls its `AbortController.abort()`.
4. Handler sends `chat:reset-with-seed { text, prompt, source: 'hotkey' }` to the renderer.
5. Handler calls `showMainWindow()` (show + focus + `activationPolicy('regular')`).

The renderer's `useChatStore.resetWithSeed({text, prompt})` clears `messages`, appends `{role:'system', content: prompt}` and `{role:'user', content: text}`, then kicks off an AI request. This matches today's `TextSelectionService` behaviour byte-for-byte from the user's perspective.

Special case: the `id === 0` hotkey (today: "open empty popup") becomes "show + focus + reset to empty conversation." No text/prompt seeded. `chat:reset-with-seed` accepts `undefined` for both fields.

### 1.5 Tray

Tray icon logic is preserved verbatim from today's `main.ts` (macOS template, Windows theme-aware, Linux fallback). Menu items:

- **Show SnapMind** — `showMainWindow()` (new item; useful when window is hidden and there's no hotkey configured).
- **Settings...** — `showMainWindow()` then IPC `nav:go('/settings/general')` to route the store there.
- **Quit** — sets `app.isQuitting = true`, closes windows, `app.quit()`.

Dock menu on macOS gets the same three items.

## §2. Routing & information architecture

### 2.1 Routes

`App.tsx` keeps `HashRouter` (Electron `file://` compatibility). Route table:

```tsx
<Routes>
  <Route path="/" element={<Navigate to="/chat" replace />} />
  <Route path="/chat" element={<ChatPopup />} />
  <Route path="/settings/*" element={<Settings />} />
  <Route path="/chatpopup" element={<Navigate to="/chat" replace />} /> {/* back-compat */}
</Routes>
```

The `/chatpopup` redirect keeps existing deep-links / bookmarks / dev URLs working during the transition.

### 2.2 Chat surface header

`src/pages/ChatPopup/ChatPopup.tsx` (name and location preserved) gains a top header row for chrome only. Phase 1 minimises visual changes:

- Left: SnapMind title / logo (thin, ~28px header).
- Right: `⚙` icon button → `useNavigate()('/settings/general')`.

The **model select stays in the bottom composer** where it lives today; moving it to the header is deferred (candidate follow-up when Agents land in Phase 3, since agent+model selection will get its own affordance then).

The Settings surface gets a back-arrow (`←`) in its header that navigates to `/chat`.

### 2.3 First-launch UX

`ChatPopup` renders an empty-state when `settings.providers` has no provider with both `apiKey` and at least one model configured. The empty-state is inline in the messages area:

> No provider configured yet.
> **[Open Settings]** to add a model, then hit **⌘⇧E** or type below.

Clicking the button routes to `/settings/models`. No forced modal, no first-run wizard in Phase 1.

## §3. State model

### 3.1 Two stores

Both live in `src/stores/`. Both are plain Zustand (no middleware other than `subscribeWithSelector` where needed) unless a specific need justifies more.

**`useSettingsStore`** — mirror of main's persisted state.

```ts
interface SettingsStoreState {
  settings: Setting;                  // shape unchanged from today
  hotkeys: Hotkey[];                  // shape unchanged from today
  permissions: SystemPermission[];    // from permission:check
  isHydrated: boolean;

  hydrate(): Promise<void>;                                 // called once from main.tsx
  updateSetting(path: (string | number)[], value: any): Promise<void>;
  updateHotkey(path: (string | number)[], value: any): Promise<void>;
  updateSettings(next: Setting): Promise<void>;             // whole-blob write (rare)

  _applyRemoteSettings(next: Setting): void;                // called from settings:updated
  _applyRemotePermissions(next: SystemPermission[]): void;  // called from permission:changed
}
```

Rules:

- No component reads `window.electronAPI.getSettings()` or `getHotkeys()` directly. Everything flows through the store. Enforced by convention, not lint (per user preference).
- **Secret handling matches today's behaviour** — `SettingsService` in main decrypts `providers[i].apiKey` on read (via `processApiKeys(..., false)`) and returns them to the renderer, and the renderer's Zustand store holds the decrypted values in memory (this is how `AIService` currently gets them for HTTP calls). Only `general.azureApiKey` is scrubbed in `hydrate()` and `_applyRemoteSettings()`, mirroring `SettingsManager`'s existing `azureApiKey = ''` pattern. Hardening ("secrets never leave main") is Phase 4's job — when AI orchestration moves to main, the store no longer needs the keys and we can strip them then.
- `updateSetting`/`updateHotkey` are optimistic: mutate the store immediately, then IPC. If the IPC rejects, revert. The subsequent `settings:updated` broadcast (still fired by main; §5) is idempotent — `_applyRemoteSettings` uses a shallow-merge that leaves in-flight optimistic writes intact.

**`useChatStore`** — pure renderer transient state.

```ts
interface ChatStoreState {
  messages: Message[];
  input: string;
  images: ImageAttachment[];
  loading: boolean;
  autoScroll: boolean;
  reasoningEnabled: boolean;
  webSearchEnabled: boolean;
  currentProviderId: string | null;
  currentModelId: string | null;
  abortController: AbortController | null;

  setInput(v: string): void;
  addImages(files: File[]): Promise<void>;
  removeImage(i: number): void;
  setAutoScroll(v: boolean): void;
  setReasoning(v: boolean): void;             // also writes to settingsStore.updateSetting
  setWebSearch(v: boolean): void;             // also writes to settingsStore.updateSetting
  setModel(providerId: string, modelId: string): void;  // also writes settingsStore.updateSetting

  send(): Promise<void>;                      // wraps AIService.sendMessageToAI
  abort(): void;
  resetWithSeed(seed?: { text?: string; prompt?: string }): Promise<void>;
}
```

`send()` and `resetWithSeed()` internally construct an `AIService` from the current `useSettingsStore.getState().settings` (still renderer-side in Phase 1) and call it — this is the only place `AIService` is instantiated in Phase 1. `abort()` calls `abortController?.abort()`.

### 3.2 Hydration

`src/main.tsx` (React entry) awaits `useSettingsStore.getState().hydrate()` before rendering `<App />`. `hydrate()` calls `settings:get`, `hotkeys:get`, `permission:check` in parallel, populates the store, subscribes to `settings:updated`, `permission:changed`, `theme:changed`, and flips `isHydrated`. A `<Spinner>` shows during hydration (same as today's `ServiceProvider` loading state).

### 3.3 Cross-cutting side effects

- Theme: `useSettingsStore` doesn't own theme; `App.tsx`'s existing `ThemeService.initialize(setTheme)` subscription is kept. Native theme change events still come via `theme:changed`.
- AutoUpdate: today's `AutoUpdateManager` becomes a plain module singleton (or a tiny third store `useUpdateStore` if state grows). Its `initialize()` is called from `main.tsx` after hydration. `useAutoUpdate` hook is rewritten to read the store instead of context.

- `hotkeys.default.json`, `settings.default.json` — schema unchanged.

- `src/services/AIService.ts` — same class, same signature, same call site (`useChatStore.send`).
- All Icon usage rules (`src/components/Icon.tsx` remains the only entry point).

## §5. Backwards compatibility

- **Config files:** unchanged. `SettingsService` continues to read `settings.json` and `hotkeys.json` and merge with defaults. No migration script needed.
- **`settings:updated` broadcast:** kept. Main still sends it (though there's now only one `webContents` to receive it), and `_applyRemoteSettings` is idempotent. Preserving this channel means later phases can nudge the renderer from background writes (SQLite migrations on startup, autoupdate touching the config, etc.) without a bespoke IPC per source.
- **Deep links / dev URLs:** the old `/chatpopup` hash route still resolves via a redirect (§2.1).
- **Encrypted secrets:** `SafeStorage` pipeline unchanged. Renderer continues to receive decrypted `providers[i].apiKey` values from `settings:get` (matches today; hardening deferred to Phase 4).

## §6. Testing plan

New:

- `useSettingsStore.test.ts` — `hydrate()` calls all three IPCs; `updateSetting()` is optimistic + reverts on rejection; `_applyRemoteSettings` merges idempotently; API keys are stripped before landing in the store.
- `useChatStore.test.ts` — `resetWithSeed({text, prompt})` clears + seeds correctly; `send()` appends user + placeholder assistant messages; `abort()` triggers the abort controller.
- `hotkeyFlow.test.ts` — mocks `execFile` for the helper binary, asserts main emits `chat:reset-with-seed` with the parsed payload and calls `window.show()`.

Kept:

- All existing `SettingsService` tests.
- All provider adapter/parser tests.
- ChatMessage / MessageActions tests.

Manual smoke test checklist (for beta.1 tagging):

1. Fresh install on macOS + Windows — window appears, tray icon appears.
2. Configure a provider in Settings → return to Chat → hotkey with selection → response streams.
3. Hit hotkey mid-stream → previous stream aborts, new conversation seeded.
4. Close window (red button / X) → app persists in tray; hotkey still works.
5. Quit via tray > Quit → process exits.
6. Upgrade path: install v0.6-beta.1 over v0.5.x → settings and hotkeys load unchanged.

## §7. Risk register

| Risk                                                                                          | Mitigation                                                                                                                    |
|-----------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| `HashRouter` back-arrow inside `/settings/*` history could accidentally exit the app.         | The Settings back button uses `navigate('/chat')`, not `navigate(-1)`. Browser-history semantics never leak to window-level.  |
| Users used to two windows may miss the "open Settings in a separate window" affordance.       | Documented in release notes; window is resizable large enough for a settings-first workflow.                                  |
| Optimistic store writes get out of sync with disk if IPC fails silently.                      | All IPC handlers return `{success, error}`; store reverts on `success:false`; failures are logged via `LoggerService`.        |
| Hotkey pressed before renderer hydrates.                                                      | Main buffers one pending `chat:reset-with-seed`; renderer replays after `hydrate()` completes. Alternative: block hotkey registration until renderer signals ready (added complexity; not preferred). |
| Tray > Settings jumps into `/settings/general` but window was previously on `/chat` with pending input — user loses draft. | Draft input persists in `useChatStore.input`; navigating away doesn't clear it.                                              |

## §8. Dependencies to install

- `zustand` (production dep). No native modules. Add via `npm install zustand`.

No other new dependencies in Phase 1.

## §9. Implementation order (proposed; the plan will refine)

1. Add `zustand`; scaffold `useSettingsStore` + `useChatStore` alongside the existing `ServiceProvider` (dual-write phase, no consumers migrated yet).
2. Migrate `Settings.tsx` + sub-pages to read from the store; verify parity.
3. Migrate `ChatPopup.tsx` to read from the store; verify parity.
4. Delete `ServiceProvider`, `SettingsManager`, `useSettings` hook.
5. Rewrite `main.ts` around a single `mainWindow`; introduce hide-on-close + `isQuitting`.
6. Rewrite hotkey path to send `chat:reset-with-seed` on the main window; fold `TextSelectionService` in.
7. Prune `preload.ts`; update all `window.electronAPI.*` call sites the pruning touches.
8. Add ⚙ button in `ChatPopup` header; add back arrow in `Settings`; add `/chatpopup` redirect.
9. Wire tray menu to `showMainWindow` + `nav:go`.
10. First-launch empty-state in `ChatPopup`.
11. Tests (stores + hotkey flow).
12. Manual smoke test; tag `0.6.0-beta.1`.

## §10. Out of scope (belongs to a later phase or a follow-up)

- SQLite storage (Phase 2).
- Agent domain model (Phase 3).
- Providers on `@ai-sdk` and AI-in-main (Phase 4).
- MCP + skills tool calling (Phase 5).
- Chat history persistence, session tabs, or resumable conversations.
- Any change to `hotkeys.default.json` / `settings.default.json` schema.
- Lint-enforcement of the "no direct `electronAPI` outside stores" convention.
