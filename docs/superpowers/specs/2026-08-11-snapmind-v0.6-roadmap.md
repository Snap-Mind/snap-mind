# SnapMind v0.6 — Release Roadmap

Status: approved decomposition
Owner: Louis Liu
Last updated: 2026-08-25

## Purpose

v0.6 is a major release that turns SnapMind from a "hotkey-launches-a-prompt" tool into an "agent-based application." The scope touches every layer (window model, state, storage, provider layer, and agent runtime), so this release is decomposed into **five sequenced phases**, each of which is its own spec + plan + implementation cycle and ships as its own beta on the `v0.6.0-beta.N` channel.

This document is the stable reference the individual phase specs link back to. It intentionally stays high-level.

## Two architectural decisions that shape every phase

1. **Single window, no cross-window sync.** The `Settings` + `ChatPopup` split is gone. One `BrowserWindow` renders both surfaces via routes. Cross-window state broadcasting (today's `settings:updated` fan-out) is retired — the store in the single renderer is the client-side source of truth. The window is always alive (tray-resident); close hides it, `Cmd+Q` / tray > Quit truly quits.
2. **AI orchestration moves to the main process.** `AIService` + `ProviderFactory` + (later) `@ai-sdk` + MCP tool hosts all run in Node/main. The renderer talks to them via typed IPC (streamed tokens, tool events, abort). Reasons: MCP transports need Node subprocess/stdio access, `@ai-sdk` is server-side-friendly, and secrets never touch the renderer.

Phase 1 delivers (1). Phase 4 delivers (2). Everything else fits around these.

## Phase-to-phase dependencies

```
Phase 1 (single window + Zustand)
    ↓
Phase 2 (SQLite) ──────┐
    ↓                  │
Phase 3 (Agent model) ─┤ (agents table needs SQLite)
    ↓                  │
Phase 4 (@ai-sdk, AI-in-main) ─── (agent runtime needs the ai-sdk request builder)
    ↓
Phase 5 (Tools) ─── (tool loop needs @ai-sdk + agent.allowedTools)
```

## What each phase deliberately _doesn't_ do

- **Phase 1** doesn't touch storage, providers, or agents. Pure UI + state refactor. Existing JSON files load unchanged.
- **Phase 2** doesn't change any UI surface or the settings/hotkeys schema shape — it swaps the backing store only.
- **Phase 3** doesn't touch the provider layer and adds no tool support. Agents are still executed by today's `AIService` — the agent's `instructions` become the system prompt, `model_provider_id`/`model_id` pick the model.
- **Phase 4** doesn't add MCP or skill loading. It's a like-for-like provider rewrite so we control less code and gain `@ai-sdk`'s tool-use surface for Phase 5.
- **Phase 5** doesn't build a marketplace or a permission UI beyond an allowlist-per-agent (and optional per-invocation consent). Skill authoring UX is a follow-up.

## Dev-time dependencies the user may need to install

Aggregated across phases so we can request them once each phase begins:

- Phase 1: `zustand` (renderer). No native modules.
- Phase 2: `better-sqlite3` (native; electron-rebuild), `drizzle-orm`, `drizzle-kit`.
- Phase 4: `ai` (Vercel AI SDK), `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, `@ai-sdk/azure`, `@ai-sdk/deepseek` or `@ai-sdk/openai-compatible` for DeepSeek/Qwen, plus `ollama-ai-provider`. Some may bundle: exact set finalised in the Phase 4 spec.
- Phase 5: `@modelcontextprotocol/sdk` (MCP client). Skills use no new deps — plain file I/O + `@ai-sdk` `tool()`.
