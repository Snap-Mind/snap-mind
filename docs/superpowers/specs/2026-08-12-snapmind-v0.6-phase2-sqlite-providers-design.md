# SnapMind v0.6 Phase 2 — SQLite for providers & models

Status: design approved, ready for planning
Owner: Louis Liu
Last updated: 2026-08-12
Parent: [`2026-08-11-snapmind-v0.6-roadmap.md`](./2026-08-11-snapmind-v0.6-roadmap.md)

## Goal

Move provider and model configuration out of `settings.json` and into a SQLite database at `userData/snapmind.db`, managed by Drizzle ORM. Keep the renderer's provider shape stable (an array of provider objects with nested models), preserve `SafeStorage` encryption for API keys, and establish the migration framework that Phases 3–5 will build on.

## Non-goals

- No change to `hotkeys.json`. Hotkeys stay in JSON; Phase 3 handles hotkeys + agents together.
- No change to the rest of `settings.json` (`general`, `appearance`, `chat`, etc.). Those stay in JSON.
- No agent domain model, no `@ai-sdk` rewrite, no MCP, no tool calling. Phases 3–5.
- No new user-facing Settings pages, no UI redesign, no i18n changes beyond removing dead `foundry` strings.
- Renderer-visible provider shape stays as `[{ id, kind, name, host, apiKey, description?, apiVersion?, projectName?, entraScope?, config?, models: [...] }]`. The only shape change is that `id` is a number and there is a new `kind` string.

## Success criteria

1. On fresh install (no `settings.json`, no DB), the 7 built-in providers (openai, azure-openai, anthropic, google, deepseek, qwen, ollama) appear in Settings > Models with empty API keys and empty model lists.
2. On upgrade from `0.6.0-beta.1` (existing `settings.json` with `providers`), every user-configured provider **except foundry** appears in the DB with its API key, host, config, and models preserved byte-for-byte. `settings.json` is rewritten without `providers`, with `chat.defaultProviderId`/`chat.defaultModelId` resolved to the new numeric IDs, and a `settings.json.pre-sqlite.bak` is left on disk next to the rewritten file.
3. Chat still works end-to-end after upgrade: hotkey → renderer → `ProviderFactory.adapterMap[provider.kind]` → correct HTTP call.
4. All API keys are encrypted at rest in the DB via `SafeStorage`. `sqlite3` CLI on the raw DB file cannot recover plaintext keys.
5. Deleting `userData/snapmind.db` and relaunching produces a fresh seeded DB (7 built-ins, empty API keys) with no crash.
6. Foundry adapter, parser, page, tests, and i18n strings are removed from the tree.
7. Existing Vitest suites pass; new suites cover schema, `ProvidersService`, one-shot import, and `useProvidersStore`.

## §1. Storage layer

### 1.1 File & connection

- Location: `userData/snapmind.db` (same directory as `settings.json`; survives `SettingsService.stabilizeUserDataAndMigrate` folder rename since it uses the same base path).
- Client module: `electron/db/client.ts` — module-scoped singleton. Opens once on app-ready, closes on `before-quit`.
- Pragmas set at open: `journal_mode = WAL`, `foreign_keys = ON`, `synchronous = NORMAL`.
- Drizzle instance: `drizzle(sqliteClient, { schema })`.

### 1.2 Schema — `electron/db/schema.ts`

```ts
import { sqliteTable, integer, text, uniqueIndex } from 'drizzle-orm/sqlite-core';

export const providers = sqliteTable('providers', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  kind: text('kind').notNull(),           // dispatch key for ProviderFactory.adapterMap
  name: text('name').notNull(),
  host: text('host'),
  apiKey: text('api_key'),                // SafeStorage base64 ciphertext; NULL when unset
  description: text('description'),
  configJson: text('config_json'),        // JSON: { apiVersion?, projectName?, entraScope?, config? }
  sortOrder: integer('sort_order').notNull(),
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
});

export const providerModels = sqliteTable(
  'provider_models',
  {
    id: integer('id').primaryKey({ autoIncrement: true }),
    providerId: integer('provider_id')
      .notNull()
      .references(() => providers.id, { onDelete: 'cascade' }),
    modelId: text('model_id').notNull(),         // API identifier, e.g. "gpt-4"
    name: text('name').notNull(),
    type: text('type'),                          // "chat" today
    capabilitiesJson: text('capabilities_json'), // JSON array of ModelCapability
    description: text('description'),
    sortOrder: integer('sort_order').notNull(),
    createdAt: integer('created_at').notNull(),
    updatedAt: integer('updated_at').notNull(),
  },
  (t) => ({
    uniqPerProvider: uniqueIndex('provider_models_provider_model_unique').on(t.providerId, t.modelId),
  })
);

export type ModelCapability = 'chat' | 'reasoning' | 'vision' | 'tools' | 'image';
```

Rationale:

- Numeric PK + `kind` column decouples adapter dispatch from row identity, so users can have two providers of the same kind (e.g. two Foundry-compatible endpoints, if Foundry ever returns) without ambiguity.
- `configJson` catches the long tail of provider-specific fields (`apiVersion`, `projectName`, `entraScope`, `config.topK`) without widening the table with mostly-null columns.
- `capabilitiesJson` stores an array. The SnapMind capability enum is local; Vercel AI SDK does not expose a canonical per-model capability list.
- `sortOrder` preserves display order (JSON arrays have inherent order; tables don't).
- `(provider_id, model_id)` is unique — one model id per provider.

### 1.3 Migrations

- Managed by `drizzle-kit`. `drizzle.config.ts` at repo root:
  ```ts
  export default { dialect: 'sqlite', schema: './electron/db/schema.ts', out: './electron/db/migrations' };
  ```
- Dev workflow: after editing `schema.ts`, run `npm run db:generate` (wraps `drizzle-kit generate`), commit the resulting SQL under `electron/db/migrations/`.
- Runtime: on app-ready, before any read/write, `migrate(db, { migrationsFolder })` runs. `migrationsFolder` resolves to `process.resourcesPath` in packaged builds and `process.cwd()/electron/db/migrations` in dev.
- Migration `.sql` files ship as `extraResources` in `electron-builder.yml` (build config) so they're available on disk at runtime.
- First migration `0000_init.sql`: `CREATE TABLE providers`, `CREATE TABLE provider_models`, `CREATE UNIQUE INDEX provider_models_provider_model_unique`. Includes seed `INSERT` statements for the 7 built-in providers with `api_key = ''`, `config_json` populated per provider. No models seeded.

### 1.5 Seed vs. import — deciding at startup

At app-ready, after `migrate()` finishes:

```
if providers row count == 0:
    if settings.json exists AND settings.json.providers is a non-empty array:
        runImport()          # see §3
    else:
        # migration seeded the built-ins; nothing to do
```

A `settings.json` top-level flag `builtinsSeeded: true` is written by `SettingsService` immediately after either (a) `runImport()` completes or (b) the "nothing to do" branch is taken (meaning the init migration's seed rows are in place). On subsequent launches, if `providers` count is 0 and `builtinsSeeded` is true (state drift — user deleted the DB), the init migration reruns against the fresh DB and seeds are recreated; the flag matches reality again. No custom re-seed path is needed.

### 1.6 Native module build

- New runtime dep: `better-sqlite3`.
- New dev deps: `drizzle-kit`, `drizzle-orm` (drizzle-orm is a runtime dep; drizzle-kit is dev-only), `@types/better-sqlite3`, `@electron/rebuild`.
- `postinstall` script: `electron-rebuild -f -w better-sqlite3` — makes the ABI match Electron's Node when devs run `npm install`. `electron-builder` handles rebuild during production packaging automatically.
- `vite.config.main.ts` marks `better-sqlite3` as external (`build.rollupOptions.external`) so it's `require()`-loaded at runtime, not bundled.

## §2. Service layer

### 2.1 `electron/ProvidersService.ts` (new)

Single-responsibility service owning all provider/model I/O. Owns the DB client (via `electron/db/client.ts`). Public surface:

```ts
class ProvidersService {
  async list(): Promise<ProviderDTO[]>;
  async create(input: CreateProviderInput): Promise<ProviderDTO>;
  async update(id: number, patch: UpdateProviderPatch): Promise<ProviderDTO>;
  async delete(id: number): Promise<void>;
  async upsertModel(providerId: number, model: UpsertModelInput): Promise<ModelDTO>;
  async deleteModel(providerId: number, modelId: number): Promise<void>;
  async resolveDefault(
    defaultProviderId: number | null,
    defaultModelId: number | null
  ): Promise<{ providerId: number; modelId: number } | null>;
  async importFromJson(
    providersFromSettings: unknown[]
  ): Promise<{ imported: number; skipped: string[] }>;
}
```

DTO shape (single source of truth for renderer contract):

```ts
type ProviderDTO = {
  id: number;
  kind: string;                        // "openai", "azure-openai", ...
  name: string;
  host: string | null;
  apiKey: string | null;               // decrypted for the renderer
  description: string | null;
  apiVersion?: string;                 // unpacked from configJson
  projectName?: string;                // unpacked from configJson
  entraScope?: string;                 // unpacked from configJson
  config?: Record<string, unknown>;    // unpacked from configJson
  models: ModelDTO[];
};

type ModelDTO = {
  id: number;
  modelId: string;
  name: string;
  type: string | null;
  capabilities: ModelCapability[];
  description: string | null;
};
```

Behavior notes:

- `list()` joins `providers` + `provider_models` (ordered by `sort_order`, then `id`), decrypts `apiKey` per row via `SafeStorageService.decrypt`, JSON-parses `configJson` and unpacks into named fields, JSON-parses `capabilitiesJson`.
- `create`/`update` do the inverse: pack named fields back into `configJson`, encrypt `apiKey` before write, `updated_at = Date.now()`. `sortOrder` on `create` = current max + 10.
- `delete` is `DELETE FROM providers WHERE id = ?` (CASCADE removes models).
- `upsertModel` uses SQLite `ON CONFLICT(provider_id, model_id) DO UPDATE`.
- `resolveDefault` is the DB-native replacement for today's `SettingsService.ensureDefaultChatModel`. Given the persisted `chat.defaultProviderId`/`chat.defaultModelId` from `settings.json`, it verifies the row still exists; if not, it falls back to the first provider that has any models, then to the first provider period. Returns `null` if there are zero providers.
- `importFromJson` implements §3.

### 2.2 `SettingsService` — what changes

`SettingsService` shrinks. It no longer knows about providers:

- Delete `processApiKeys` (moved into `ProvidersService`, per-row).
- Delete `ensureDefaultChatModel` (moved to `ProvidersService.resolveDefault`).
- `initializeConfigs` no longer touches `providers`. It still handles `general`, `appearance`, `chat`, `hotkeys`, system-locale defaulting, deep-merge with defaults, and the folder-rename migration.
- After `mergeDeep`, `SettingsService` calls `ProvidersService.resolveDefault(settings.chat.defaultProviderId, settings.chat.defaultModelId)`. If it returns a pair, and that pair differs from the persisted values, `SettingsService` writes the resolved IDs back to `settings.json`. If it returns `null` (no providers at all — impossible after migrations run, but defensive), the two `defaultProviderId`/`defaultModelId` fields stay `null`; the renderer's chat surface handles that as "no default configured".
- `updateSetting(path, value)` continues to work for all non-`providers` paths. If `path[0] === 'providers'`, it throws — with a clear error pointing to the dedicated IPC channels. This is a bug-catcher for missed migrations, not a public API.

### 2.3 IPC contract — `preload.ts` additions

```ts
// invoke (renderer → main)
providers:list      → ProviderDTO[]
providers:create    (input: CreateProviderInput)       → ProviderDTO
providers:update    (id: number, patch: UpdateProviderPatch) → ProviderDTO
providers:delete    (id: number)                       → void
models:upsert       (providerId: number, model: UpsertModelInput) → ModelDTO
models:delete       (providerId: number, modelId: number) → void

// broadcast (main → renderer)
providers:changed   ProviderDTO[]   // fired after any successful mutation
```

The renderer only reads/writes providers via these channels — never via `updateSetting`. Convention only, no lint rule; the `SettingsService` throw at §2.2 is the runtime backstop.

## §3. One-shot import from `settings.json`

Runs at most once per install, after migrations complete, only when `providers` count is 0 AND `settings.json.providers` is a non-empty array.

```
1. Read settings.json (raw file; do NOT run current processApiKeys decrypt — we want to preserve the on-disk encrypted bytes and re-store them as-is).
2. Backup: fs.copyFileSync(settings.json, settings.json.pre-sqlite.bak).
   If backup write throws, abort import; leave DB empty; log error.
3. BEGIN TRANSACTION.
4. For each entry p in settings.json.providers:
     if p.id === 'foundry': push 'foundry' onto skipped[], continue.
     newProviderId = INSERT providers (
       kind         = p.id,
       name         = p.name,
       host         = p.host ?? null,
       api_key      = p.apiKey ?? null,     // already encrypted base64 from JSON era
       description  = p.description ?? null,
       config_json  = JSON.stringify(pickConfigFields(p)) or null,
       sort_order   = 10 * index,
       created_at   = now, updated_at = now
     ).
     mapOldToNew[p.id] = newProviderId.
     For each m in p.models ?? []:
       INSERT provider_models (
         provider_id       = newProviderId,
         model_id          = m.id,
         name              = m.name,
         type              = m.type ?? null,
         capabilities_json = JSON.stringify(m.capabilities ?? []),
         description       = m.description ?? null,
         sort_order        = 10 * modelIndex,
         created_at = now, updated_at = now
       ).
       mapOldModel[p.id + '|' + m.id] = newModelPkId.
5. COMMIT TRANSACTION. (After this point the DB is authoritative.)
6. Rewrite settings.json:
     - Remove settings.providers.
     - If settings.chat.defaultProvider (string) and settings.chat.defaultModel (string) exist:
         defaultProviderId = mapOldToNew[settings.chat.defaultProvider] ?? null
         defaultModelId    = mapOldModel[defaultProvider + '|' + defaultModel] ?? null
       Otherwise: defaultProviderId = null, defaultModelId = null.
     - Delete settings.chat.defaultProvider, settings.chat.defaultModel.
     - Write settings.chat.defaultProviderId, settings.chat.defaultModelId.
     - Set settings.builtinsSeeded = true.
   fs.writeFileSync atomically (write to .tmp then rename).
7. Log: "[phase2-import] imported N providers, M models; skipped: [foundry]".
```

`pickConfigFields(p)`:

```ts
function pickConfigFields(p: any): Record<string, unknown> | null {
  const cfg: Record<string, unknown> = {};
  if (p.apiVersion !== undefined) cfg.apiVersion = p.apiVersion;
  if (p.projectName !== undefined) cfg.projectName = p.projectName;
  if (p.entraScope !== undefined) cfg.entraScope = p.entraScope;
  if (p.config !== undefined) cfg.config = p.config;
  return Object.keys(cfg).length === 0 ? null : cfg;
}
```

Failure semantics:

- If step 2 fails: no writes happen, JSON untouched. App still starts (renderer sees the seeded built-ins from the migration, not the user's data). Escape hatch: fix disk permissions, delete `snapmind.db`, relaunch.
- If step 3–5 fails: transaction rolls back, DB is empty, JSON untouched. Retry on next launch.
- If step 6 fails after step 5 commits: DB has the user's data, JSON still has the legacy `providers` array. Next launch sees `providers` count > 0, skips import, and `SettingsService` ignores the stale `settings.providers` field (only `defaultProviderId`/`defaultModelId` matter to it). This is degraded but functional; a warning log lets support diagnose it.

## §4. Renderer

### 4.1 New store — `src/stores/useProvidersStore.ts`

Mirror the pattern of `useSettingsStore`. Skeleton:

```ts
type ProvidersState = {
  providers: ProviderDTO[];
  hydrated: boolean;
  hydrate: () => Promise<void>;
  createProvider: (input: CreateProviderInput) => Promise<ProviderDTO>;
  updateProvider: (id: number, patch: UpdateProviderPatch) => Promise<ProviderDTO>;
  deleteProvider: (id: number) => Promise<void>;
  upsertModel: (providerId: number, model: UpsertModelInput) => Promise<ModelDTO>;
  deleteModel: (providerId: number, modelId: number) => Promise<void>;
};
```

- Hydration on renderer boot: `hydrate()` calls `electronAPI.providers.list()` and populates `providers`.
- Subscribes to `providers:changed` once at store creation; every broadcast replaces `providers` wholesale. Since `list()` is cheap (7 rows + a few models) and the payload arrives with each broadcast, we don't need optimistic updates.
- Component consumers: `useProviders()` returns `providers`; individual action hooks (`useCreateProvider`, etc.) or direct store access as needed. Selectors mirror the `useSettingsStore` style.

### 4.2 `useSettingsStore` — what changes

- Remove `settings.providers` from the shape.
- Add `settings.chat.defaultProviderId: number | null` and `settings.chat.defaultModelId: number | null`.
- Remove any selectors/actions that were touching `providers`.
- Hydration flow is otherwise identical (same `settings:get` / `settings:updated` channels).

### 4.3 Component migrations

Every call site under `src/` that touches `settings.providers` moves to `useProvidersStore`. Known call sites (grep `settings.providers` and `updateSetting(['providers'`):

- `src/pages/Settings/Models/SettingsModels.tsx` — provider list + model tables. Read `providers` from `useProvidersStore`; write via dedicated actions.
- `src/pages/Settings/Models/ProviderOpenAI.tsx`, `ProviderAzureOpenAI.tsx`, `ProviderAnthropic.tsx`, `ProviderGoogle.tsx`, `ProviderDeepSeek.tsx`, `ProviderQwen.tsx`, `ProviderOllama.tsx` — per-provider config forms. Read + write via `useProvidersStore`.
- `src/pages/Settings/Models/ProviderFoundry.tsx` — deleted (§5).
- `src/components/ModelTable.tsx` — read via `useProvidersStore`, write via `upsertModel` / `deleteModel`.
- `src/pages/ChatPopup/ChatPopup.tsx` — reads current provider to display name / configure request; switches from `settings.providers.find(p => p.id === settings.chat.defaultProvider)` to `providers.find(p => p.id === settings.chat.defaultProviderId)`.
- `src/services/AIService.ts` (and downstream `ProviderFactory`) — receives a `ProviderDTO` from the renderer; changes any `provider.id`-as-string lookup to `provider.kind`.
- `src/services/providers/ProviderFactory.ts` — `adapterMap[provider.kind]` (was `adapterMap[provider.id]`).

## §6. Error handling & recovery

| Situation                                      | Behavior                                                                                                                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Database(dbPath)` throws (locked/corrupt)     | Log via `logService.error`. Show native `dialog.showMessageBoxSync` with "Open user data folder" + "Quit" buttons. Do not proceed to renderer boot.                                         |
| `migrate()` throws                             | Same treatment as above.                                                                                                                                                                    |
| Import step 2 (backup write) throws            | Skip import; log warn; renderer shows the seeded built-ins. User's `settings.json` untouched.                                                                                               |
| Import steps 3–5 (DB writes) throw             | Transaction rolls back; log error; app continues with empty DB; retry on next launch.                                                                                                       |
| Import step 6 (JSON rewrite) throws            | DB committed; JSON left with stale `providers` field. Next launch skips import (providers count > 0). Logged as a warning; support-diagnosable.                                             |
| `safeStorage.isEncryptionAvailable() === false`| Match today's behavior in `SafeStorageService`: pass-through plaintext for `api_key` field, log warn once.                                                                                  |
| `providers:update` with unknown `id`           | Throw a typed IPC error. Preload validates `id` is a positive integer; renderer surfaces a toast on the invoke rejection.                                                                   |
| User deletes `userData/snapmind.db`            | Next launch: init migration reruns against the fresh DB, recreating schema and seed rows automatically (drizzle sees an empty `__drizzle_migrations` table). `settings.json` still has `chat.defaultProviderId` pointing at a now-nonexistent row; `resolveDefault` picks the first seeded provider and writes the resolved id back.                                                                                                     |
